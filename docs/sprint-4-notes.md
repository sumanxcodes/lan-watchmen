# Sprint 4: Detection Rules

## Goal
Write Wazuh detection rules to alert on the new events generated in Sprint 3 (new device detection) and Sprint 2 (repeated malicious DNS blocks).

## What was done

### 1. New Device Rule (`local_rules.xml`)
Wazuh natively parses JSON logs and maps them to the Suricata rule group (`86600`) if they contain an `event_type` field. To detect the new device events generated by our `device-inventory` script, we created a rule that inherits from `86600` and specifically matches `new_device`:

```xml
<group name="device_inventory,">
  <rule id="100002" level="8">
    <if_sid>86600</if_sid>
    <field name="event_type">new_device</field>
    <description>New unknown device detected on the network: $(mac_address) ($(ip_address))</description>
  </rule>
</group>
```

### 2. Repeated Malicious DNS Blocks (`pihole-rule.xml`)
To detect when a device repeatedly hits blocked malware domains, we created a frequency-based child rule that triggers if the base Pi-hole block rule (`120002`) fires 5 times within a 60-second window. We added this to `pihole-rule.xml`:

```xml
    <rule id="120003" level="10" frequency="5" timeframe="60">
        <if_matched_sid>120002</if_matched_sid>
        <description>High frequency of malicious DNS requests blocked.</description>
    </rule>
```

### 3. Testing with `wazuh-logtest`
Both rules were thoroughly tested using the `wazuh-logtest` binary inside the Wazuh manager container.
- Feeding a sample JSON log generated rule `100002` (Level 8).
- Feeding 5 sequential `gravity blocked` dnsmasq logs triggered rule `120002` four times, and on the fifth time, it correctly triggered rule `120003` (Level 10).

We restarted the Wazuh manager to apply the changes to the live environment.
